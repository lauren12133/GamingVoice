# EQ 功能可行性评估

> 需求：评估能否把 EQ 做进 GamingVoice，以及**最多能做到多少段**。
> 本文所有 CPU 数字都是在本仓库实测出来的（`cargo run --release --example eq_bench`），不是估算。

---

## 一、结论

**能加，而且 CPU 根本不是瓶颈。**

| 结论 | 数字 |
|---|---|
| 推荐规格 | **每声道 10 段**参数均衡（8 路独立），另加一组**双耳 10 段**耳机校正 |
| 工程上限 | 每声道 **31 段**（对齐 Equalizer APO 的 1/3 倍频程图形 EQ），8 路共 248 个 biquad |
| 上限的瓶颈 | **不是算力**（31 段仅 2.03% 单核），是界面可操作性、数值稳定性、削波管理 |
| 额外延迟 | **0 样本**。IIR 逐样本运算，不攒块，不影响现有的 10 ms |
| 预计工作量 | 2～3 天（DSP 半天 / 面板一天 / 导入与预设半天） |

---

## 二、实测：到底吃多少 CPU

测法：8 声道 × N 段 peaking biquad（Transposed Direct Form II，RBJ cookbook），
处理 10 秒 48 kHz 信号，单线程。

| 段数/声道 | biquad 总数 | 耗时 | 实时率 | 单核占用 |
|---|---|---|---|---|
| 0（基线） | 0 | 3.6 ms | 0.0004 | 0.04% |
| 5 | 40 | 27.5 ms | 0.0028 | 0.28% |
| **10** | 80 | 54.4 ms | 0.0054 | **0.54%** |
| 15 | 120 | 83.8 ms | 0.0084 | 0.84% |
| **31** | 248 | 203.1 ms | 0.0203 | **2.03%** |

加上现有的 HRIR 卷积（8→2，实测约 0.3%～1%），**满配 31 段的总占用仍在 3% 单核以内**。

也就是说：算力允许的段数远超"人耳能调得过来"的段数。

---

## 三、两个插入位置，意义完全不同

EQ 放哪儿，决定了它能做什么：

### A. 每声道 EQ（卷积之前）

```
bus[0..8] → 每声道 EQ（8 组级联）→ 每声道增益 → HRIR → 双耳
```

- 能改**某个方向的声音特征**：只削后方的低频轰鸣、只给中置抬人声清晰度。
- 成本 ×8（这就是上表的数字）。
- 语义上和 Equalizer APO 的 `Channel: BL` + `Filter:` 完全一致，可以无损导入现成配置。

### B. 双耳 EQ（卷积之后）

```
... → HRIR → 双耳 L/R → EQ（2 组级联）→ 耳机
```

- 就是**耳机校正 EQ**（HeSuVi 的 `eq/*.txt` 干的事）：把耳机的频响拉平，
  让 HRIR 里的方位线索不被耳机本身的峰谷污染。
- 成本只有 A 的 1/4（2 路 vs 8 路）。
- **改不了方向**：两路都一样的曲线，只会改变整体音色。

**建议两者都要**：B 常开（一组耳机校正曲线），A 按需开（默认关，避免一上来 8×10 个旋钮吓人）。

## 四、为什么"最多 31 段"是个工程上限，不是算力上限

算力上 8×64 段也才 4% 左右。真正卡住的是这三件事：

### 1. 界面（第一约束）

8 声道 × 31 段 = **248 个推子**。现有面板一屏放 8 个推子刚好，
248 个必然要塞进多层折叠/标签页，调一次等于做一次表。

可行的做法：
- 主面板只给 **10 段**（1 倍频程），每声道一个开关；
- 31 段只在"高级"里给**单个声道**编辑（一次看一路，不是看八路）；
- 提供"复制到所有声道"。

### 2. 数值稳定性（第二约束）

f32 的 biquad 在**低频 + 高 Q** 时极点贴着单位圆，系数舍入误差会让实际频响偏离设计值：

- `fc < 60 Hz` 且 `Q > 8` 时开始明显；
- `fc < 30 Hz` 且 `Q > 12` 时可能直接不稳定（自激）。

对策（选一即可）：
- 限制 `Q ≤ 8`、`fc ≥ 20 Hz`（推荐，够用且简单）；
- 或者低频段用 f64 状态量（成本 +~30%，仍可接受）；
- 或者把低频段改用 shelving / low-shelf 而不是高 Q peaking。

### 3. 削波（第三约束）

EQ 的**提升**会直接把峰值推过 0 dBFS，而现在的链路末端只有 `makeup_db` 一个静态补偿。
需要二选一：
- EQ 增益为正时自动扣等量 makeup（简单，但整体会变小）；
- EQ 后加一个软限幅（`tanh` 近似，成本可忽略，但会引入极轻微谐波）。

建议：**默认自动 makeup**，软限幅做成开关。

## 五、实现方案（可直接落地）

### 数据结构

```rust
// dsp/eq.rs
pub struct Biquad { b0, b1, b2, a1, a2, z1, z2 }   // TDF-II，9 mul + 4 add / 样本

pub struct Band { pub fc: f32, pub q: f32, pub gain_db: f32 }

pub struct Cascade { bands: Vec<Biquad>, design: Vec<Band> }

pub struct EqBank {
  per_channel: [Cascade; 8],   // A：卷积之前
  binaural: [Cascade; 2],      // B：卷积之后
}
```

### 挂载点

在 `Spatial::render()` 里插两步（现有代码已经有清晰的分界）：

```rust
fn render(&mut self, out_l: &mut [f32], out_r: &mut [f32]) {
  self.apply_gain_and_delay();
  self.eq_ch.process(&mut self.bus);      // ← A：每声道，8 路
  self.conv.process(&self.bus, &mut self.ears);
  self.eq_ear.process(&mut self.ears);    // ← B：双耳，2 路
  ...
}
```

### 参数热更新（关键）

改 EQ 不能重建缓冲（会断音）。做法：
1. 只重算系数（`design → Biquad` 是纯算术，248 段耗时 < 1 µs）；
2. 新系数直接替换；
3. 若担心切换瞬间的轻微爆音，做 5 ms 的系数线性插值（或对输出做 2 ms 交叉淡化）。

### 导入 Equalizer APO

`src-tauri/src/compat/apo.rs` **已经能解析** `GraphicEQ: 20 0; 25 -2; ...` 和
`Filter: ON PK Fc 120 Hz Gain -4 dB Q 1.2`。所以迁移路径是现成的：

```
APO config.txt  →  compat::apo::parse()  →  Vec<Band>  →  EqBank
```

用户手里调好的 APO 配置可以一键吃进来，不用重调 —— 这是"兼容"最实在的形态。

### 预设

`Vec<Band>` 存 JSON，跟现有预设并列。建议内置三组：
- `flat`（旁路，用于 A/B）
- `headphone-correction`（一组常见的哈曼近似曲线，给 B 用）
- `footstep-boost`（给 A 的后方声道：抬 2–5 kHz、削 100–200 Hz 轰鸣）

## 六、不做什么（避免把简单问题做复杂）

- **不做 FIR 线性相位 EQ**。它会引入半个滤波器长度的延迟（1024 抽头 ≈ 10.7 ms），
  直接违背"10 ms 块"这个前提。游戏用 IIR 最小相位才是对的。
- **不做自适应/自动 EQ**。没有可信的目标曲线来源，做了也是玄学。
- **不做 8×31 的全展开界面**。技术上能画，但没人会去调。

## 七、如果要做，建议的节奏

| 阶段 | 内容 | 产出 | 估时 |
|---|---|---|---|
| P6-1 | `dsp/eq.rs`：Biquad + Cascade + 31 段图形设计 + 单测（与理论频响对比） | 可单测的 DSP | 半天 |
| P6-2 | 挂进 `Spatial::render`（A+B），参数热更新，自动 makeup | 能听出效果 | 半天 |
| P6-3 | 面板：每声道 10 段折叠 + 高级单声道 31 段 + 曲线预览 | 可操作 | 1 天 |
| P6-4 | 导入 APO `GraphicEQ` / `Filter`，预设 JSON | 迁移通道 | 半天 |

**验证方式**（这点很重要）：把 EQ 全设 0 dB，输出必须与不加 EQ 时**逐样本一致**
（误差 < 1e-6）。这条测试能挡住 90% 的"系数归一化写错"。
